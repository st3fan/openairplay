# A now-playing display with terminal artwork

Goal: show **what is currently playing** — track title, artist and album
centered on screen — plus the **cover art rendered as a real image** on
terminals that can do it (Ghostty, Kitty, WezTerm, iTerm2). Everything it
displays already exists in the library's event stream after
[20260803-03-metadata-artwork.md](20260803-03-metadata-artwork.md), except
two fields this plan adds.

> **Shape change, 2026-08-04 (phases 4–5).** Phases 1–3 built this as a
> `--tui` flag on the receiver. Stefan's call after seeing it: the display
> becomes **its own app**, `openairplay1-dashboard`, run independently of the
> receiver, with a **WebSocket** endpoint on the receiver as the seam — a
> standard one, so a web app can consume it later. The screen itself does not
> change. See [Splitting the display out](#splitting-the-display-out-phases-4-5).

Requested content on screen (all confirmed):

- title / artist / album, centered
- cover art as an image where the terminal supports it
- idle vs connected state, and the receiver's own name
- volume
- audio format (rate, channels)
- elapsed / total time
- the sender's IP address

The last two are not available today — hence a library phase before the TUI
itself.

## What already exists, and what has to be added

The binary is the library's embedder #1 and consumes only its public API;
that stays true here. Today's `Event`s give the TUI most of what it needs:
`SessionStarted { rate, channels }`, `Volume { db }`, `Metadata`, `Artwork`,
`Flushed`, `SessionEnded`. Two gaps:

**Elapsed / total time.** Senders push
`SET_PARAMETER text/parameters` with `progress: <start>/<current>/<end>` —
three RTP timestamps — whenever position changes. We advertise `md=0,1,2`
(the third being progress), so senders already send it; we currently parse
only the `volume:` line out of that body and ignore the rest. This plan adds
the parse and a new event.

Timestamps are wire concepts, and the invariant is that they stay out of the
public API, so the library converts them with the session's sample rate and
emits **durations**:

```rust
/// SET_PARAMETER progress. Position within the current track.
Event::Progress {
    elapsed: Duration,   // (current - start) / rate
    duration: Duration,  // (end - start) / rate
},
```

Senders send this every few seconds, not per frame, so the TUI extrapolates
between updates from its own clock (clamped to `duration`) and re-syncs on
each event.

**The sender's IP.** `Session` knows the peer address (it addresses resend
requests with it) but never surfaces it. The natural home is
`SessionStarted`, which is exactly the "a sender connected" moment:

```rust
#[non_exhaustive]
SessionStarted {
    rate: u32,
    channels: u8,
    peer: IpAddr,   // new
},
```

**This is a breaking change** for anyone matching
`Event::SessionStarted { rate, channels }` — the crate is published, so it
means **0.2.0**, and radiod's match arm needs `..` added when it bumps. The
alternative — a separate `Event::SenderConnected { peer }` variant, which
would be non-breaking on the `#[non_exhaustive]` enum — was considered and
rejected: two events for one moment, with an ordering question between them,
to dodge a version bump on a 0.1 crate with two known embedders. Worth
mirroring in openairplay2 later for parity; out of scope here.

> **Changed during implementation:** this plan also said to mark the
> *variant* `#[non_exhaustive]` so later fields would be additive. Doing so
> makes the variant impossible to **construct** outside the library, and
> hosts do construct it — the TUI's own layout tests build a
> `SessionStarted` to render, and radiod's tests would too. The variant is
> therefore left constructible, and a future field addition stays breaking
> (acceptable on 0.x, and the separate-variant escape hatch above remains
> available). The enum-level `#[non_exhaustive]` is untouched, so *new
> variants* are still additive.

## The TUI

**Layout.** One centered column: artwork block on top, then title (bold),
artist, album, then a dim status line. Idle state replaces the track block
with the receiver name and "waiting for a sender…". Nothing scrolls,
nothing is interactive except `q`/`Ctrl-C` to quit.

```
┌────────────────────────── 96x30 ───────────────────────────┐
│                                                            │
│                    ┌──────────────┐                        │
│                    │              │                        │
│                    │   artwork    │                        │
│                    │              │                        │
│                    └──────────────┘                        │
│                                                            │
│                      Sonata No. 1                          │
│                       Some Artist                          │
│                       Some Album                           │
│                                                            │
│                 ━━━━━━━━━━━━━━━━━━━━━━━                     │
│                    1:23 / 4:07                             │
│                                                            │
│    Living Room · 192.168.1.42 · 44100 Hz 2ch · -12.5 dB    │
└────────────────────────────────────────────────────────────┘
```

**Stack: ratatui + crossterm** (Stefan's call over a hand-rolled centering
pass) — layout constraints, and room to grow into panes or meters later. In
the binary only; the library gains no TUI dependency and stays macOS-green.

**Logging has to go somewhere else.** `env_logger` writing to stderr would
shred the screen. With `--tui`, log output is suppressed unless
`--log-file PATH` is given, in which case the logger writes there instead.
`--log-file` works without `--tui` too (it is just a sink change).

**Terminal restore is not optional.** Alternate screen + hidden cursor + raw
mode, restored on `q`, on `Ctrl-C`, on a fatal error, **and from a panic
hook** — a receiver that leaves the terminal in raw mode with no cursor on a
panic is worse than no TUI. Resize events trigger a redraw and re-place the
artwork.

## Artwork: Kitty graphics and iTerm2 inline images

Two protocols cover the terminals that matter (Stefan's call):

| Terminal | Protocol |
|---|---|
| Ghostty, Kitty | Kitty graphics (`APC _G … ST`) |
| WezTerm | either (prefer Kitty) |
| iTerm2, Konsole | iTerm2 inline images (`OSC 1337 File=inline`) |
| anything else | text only, no image |

**Format handling.** iTerm2's protocol takes the file bytes as-is, so JPEG
and PNG both pass straight through as base64 — nothing to decode. Kitty
accepts PNG (`f=100`) or raw pixels (`f=24`/`f=32`), and senders overwhelmingly
send JPEG, so the JPEG path decodes to RGB with `jpeg-decoder` (small and
focused; the `image` crate would pull far more for one format). PNG goes
through as `f=100` untouched.

**Sizing.** Both protocols can place an image into a cell box and let the
terminal scale (`c=`/`r=` for Kitty, `width=`/`height=` in cells for iTerm2),
so we never resample. To keep the aspect ratio right we need the cell pixel
size: `TIOCGWINSZ`'s `ws_xpixel`/`ws_ypixel` when the terminal fills it in,
falling back to assuming a 1:2 cell. The artwork box is capped at a fraction
of the screen so the text always fits.

**Detection.** Probe, then fall back to environment. The Kitty probe is the
protocol's own query (`a=q` with a 1×1 image) with a short read timeout; if
it answers `OK`, Kitty graphics work. Otherwise `TERM`/`TERM_PROGRAM`/
`KITTY_WINDOW_ID`/`GHOSTTY_*`/`KONSOLE_VERSION` decide, and anything
unrecognized gets text only. `--tui-images=auto|kitty|iterm2|none` forces the
choice for testing and for terminals that lie.

**Lifecycle.** Kitty images persist until deleted, so the TUI owns one image
id: delete-then-draw on track change, delete on `Artwork` with empty data
(the `image/none` clear), delete on exit. Only the latest artwork bytes are
kept in memory.

## Testing

The library phase is ordinary unit-test work: `progress:` parsing (including
malformed and out-of-order values, and `start == end`), the timestamp →
`Duration` conversion at the session sample rate, and `peer` reaching
`SessionStarted` (the existing session tests already assert on that event).

For the TUI, the parts worth testing are the ones that are pure:

- **Layout**, via ratatui's `TestBackend`: render a frame into a buffer and
  assert the centering and the content — idle vs playing, missing fields
  (title-only metadata), a very narrow terminal, and a terminal too short for
  artwork.
- **Escape-sequence builders**: assert the exact bytes for a small known
  image, both protocols, including the delete sequence. These are pure
  functions over `(bytes, placement)` and are where a typo would otherwise
  cost a hardware round trip.
- **Capability detection**, as a pure function over an env map plus an
  optional probe result, so every terminal in the table above is a test case.
- **Elapsed extrapolation**: given a `Progress` event and elapsed wall time,
  the displayed position advances and clamps at `duration`.

What can't be unit-tested is the real thing, so acceptance includes a manual
run in Ghostty (artwork appears, changes with the track, clears on
`image/none`, survives a resize, terminal restored on `Ctrl-C` and on a
forced panic) and a check in a plain `xterm` that the text-only fallback is
clean.

## Splitting the display out (phases 4–5)

The display is no longer a mode of the receiver: it is
**`openairplay1-dashboard`**, a separate binary in this workspace, started and
stopped independently, possibly on another machine. The receiver publishes
what it knows over a WebSocket; the dashboard subscribes and renders exactly
the screen phases 2–3 already built.

That buys three things beyond tidiness: the receiver can run headless under
systemd while a dashboard comes and goes; several dashboards can watch one
receiver; and the same endpoint feeds a browser later without any further
receiver work.

### The seam

**WebSocket, JSON text frames**, served by the receiver:

```
openairplay1-receiver --dashboard-listen 127.0.0.1:7392
openairplay1-dashboard --connect ws://127.0.0.1:7392
```

Off unless `--dashboard-listen` is given, and **bound to loopback in the
example on purpose** — the stream carries now-playing metadata and cover art,
which is nobody's business but the user's; binding elsewhere is the operator's
explicit choice. No authentication (out of scope, noted below).

`tokio-tungstenite` over a plain `TcpListener` is the proposed server: it is
the small, standard choice, and it is a handful of crates rather than a whole
HTTP stack. (`axum` with its `ws` feature would also serve a future web UI's
static files and an artwork URL from the same port — worth revisiting if a
browser front end actually happens, but not worth pulling `hyper`/`tower` in
today.)

### The messages

One `#[serde(tag = "type", rename_all = "snake_case")]` enum. Durations are
integer milliseconds; the artwork is base64 with its content type, so a web
client can drop it straight into an `<img src="data:…">`.

```jsonc
// Sent once, immediately on connect: everything the receiver currently knows.
// Without this, a dashboard that starts mid-track shows an empty screen until
// the next event — which for a paused-on-one-track sender may be never.
{"type":"snapshot",
 "receiver":{"name":"Living Room","version":"0.2.0"},
 "session":{"rate":44100,"channels":2,"peer":"192.168.1.42"},   // or null
 "track":{"title":"Sonata No. 1","artist":"…","album":"…"},     // or null
 "volume_db":-12.5,                                              // or null
 "progress":{"elapsed_ms":83000,"duration_ms":247000},           // or null
 "artwork":{"content_type":"image/jpeg","data_base64":"…"}}      // or null

// Then one message per change, mirroring the library's events.
{"type":"session_started","rate":44100,"channels":2,"peer":"192.168.1.42"}
{"type":"metadata","title":"…","artist":null,"album":"…"}
{"type":"artwork","content_type":"image/jpeg","data_base64":"…"}  // "" = cleared
{"type":"volume","db":-12.5}
{"type":"progress","elapsed_ms":83000,"duration_ms":247000}
{"type":"flushed"}
{"type":"session_ended"}
```

The delta messages are deliberately a near-copy of `Event`, so the dashboard's
existing `NowPlaying::apply` keeps its shape and the snapshot is the only new
state-folding code.

**Where the types live:** a new tiny workspace crate,
`openairplay1-dashboard-protocol` — serde structs and nothing else — depended on
by both binaries. One definition of the wire format, and it is what a future
web client's schema would be generated from. (Alternatives considered:
duplicating the JSON on each side, which drifts; or hanging the types off the
dashboard crate's lib target, which would drag `ratatui` into the receiver's
dependency tree.)

### Receiver side

The event task already fans events out to the gain and the display; it gains a
third consumer. State for the snapshot lives behind a mutex, updated as events
pass, and a `tokio::sync::broadcast` fans messages out to connected clients.

Two behaviours worth naming now, because both are the kind of thing that only
shows up under load:

- **A slow or dead dashboard must never stall the receiver.** The broadcast
  channel is bounded; a client that lags gets dropped from the channel, and
  the server responds by sending it a *fresh snapshot* rather than
  disconnecting it — artwork frames are hundreds of KB, and a client that
  missed one is better resynced than killed.
- **Dead connections are noticed.** A WebSocket ping on an interval, and a
  client that fails to pong within the window is dropped, so a laptop that
  closed its lid doesn't hold a slot forever.

### Dashboard side

Same screen, same tests. What is new is the connection: `--connect URL`, a
**reconnect loop with backoff** (the receiver may not be up yet, or may
restart), and a connection state on screen — "connecting to …" / "connection
lost, retrying" — reusing the existing idle layout. The receiver name in the
status line now comes from the snapshot rather than local config.

The dashboard depends on `openairplay1` for nothing at all; it is a
WebSocket client and a renderer. `ratatui`, `crossterm` and `jpeg-decoder`
move out of the receiver with it, which is a win for the headless case:
`cargo tree -p openairplay1-receiver` should have no TUI dependencies left
when phase 5 lands.

### Naming

**Settled at review: `openairplay1-dashboard`**, for consistency with
`openairplay1` and `openairplay1-receiver` (and the crates.io namespace). The
protocol crate is `openairplay1-dashboard-protocol` to match.

### Testing

- Protocol crate: serde round-trips per message, including `null` fields and
  an empty-artwork clear, plus one **fixture test** that pins the exact JSON
  bytes for each message — the point of a published protocol is that it does
  not drift silently.
- Receiver: an integration test that opens a real WebSocket to an
  ephemeral port, drives a session through the existing synthetic-sender
  helpers, and asserts the message sequence; one that connects **mid-session**
  and asserts the snapshot carries track, artwork and progress; one with two
  clients; and one where a client stops reading and the receiver keeps serving
  the other.
- Dashboard: the existing `TestBackend` layout tests move across unchanged,
  plus folding a snapshot into `NowPlaying`, and the reconnect state rendering.
- Manual: receiver and dashboard in separate terminals; kill and restart each
  in turn and watch the other recover.

## Pause (phases 9–10)

Requested after using the dashboard: pausing the sender should keep the track
on screen, stop the clock where it is, and pick up again on resume.

### There is no pause on the wire

AirPlay 1 has no working pause on the control channel. `PAUSE` is advertised
in `Public` for form's sake and answered `501`, and stock senders never send
it: pausing an iPhone simply **stops the audio packets** — usually right after
a `FLUSH` — while the RTSP connection carries on as if nothing happened.

So nothing tells us "paused". That leaves two ways to give Stefan what he
asked for, and they are not equally honest.

### The clock is already inventing data (fix this regardless)

Senders report `progress:` every few seconds; between reports the dashboard
advances the clock with its own. That is fine while audio is flowing and
**wrong the moment it isn't**: a sender that pauses without a `FLUSH` would
have its position advance on screen forever, because nothing tells the display
to stop.

The fix needs no inference and no library change:

- **Stop extrapolating when the last report goes stale.** Senders report every
  few seconds, so after (say) 10 s with no new `Progress` the display no longer
  has evidence the position is moving, and freezes it where it was.
- **`Flushed` freezes instead of clearing.** Today it sets the position to
  `None` and the bar and clock vanish. Since a pause usually arrives as `FLUSH`
  first, that blanks the clock on the way into a pause — and on a seek it
  blinks out and back. Freezing keeps the last known position on screen until
  the sender says otherwise.

That alone delivers the requested behaviour: track stays, clock stops, resumes
on the next report. What it does not give is a **label** — a frozen clock and a
stopped stream look the same, because from the wire they are the same.

### Inferring an actual "paused", and what it costs

The label needs the library to notice the audio stream going quiet — packets
arrive every ~8 ms, so a gap of a few hundred ms means the sender stopped — and
report `Event::Paused(bool)` (the shape openairplay2 already has, though it
derives it from an explicit `SETRATEANCHORTIME`).

This is a **threshold heuristic**, and worth being clear-eyed about: a network
stall long enough to cross the line shows "paused" when nothing was paused, and
the screen reacts a few hundred ms late. It is defensible — a receiver whose
audio stopped is not playing, whatever the reason — but it is a claim the wire
does not actually make, and it is only worth adding if the honest version above
turns out to feel wrong in use.

### The experiment that decides it

One capture on real hardware settles the design, and it is a minute's work:
play something, **pause**, wait, resume, with `RUST_LOG=debug`. What matters:

- Does a `FLUSH` arrive on pause, and does the position report stop?
- Does the sender keep sending `progress:` while paused (a frozen `current`
  would make the freeze exact, with no staleness window needed)?
- Does anything else arrive that marks the pause — sync packets stopping, a
  `SET_PARAMETER` we currently ignore?

If a paused sender keeps reporting a frozen position, phase 10 is unnecessary
and the honest version is also the *better* one. If it goes quiet, we can weigh
the label against the heuristic knowing exactly what we are buying.

### Out of scope

Implementing RTSP `PAUSE` (senders don't use it — `501` is correct); any
control *of* the sender from the receiver or dashboard (DACP, which would let
the dashboard pause the phone, is a separate feature needing the `DACP-ID` and
`Active-Remote` headers we currently ignore).

## Scope

In scope: `Event::Progress`; `peer` on `SessionStarted` (+ 0.2.0 bump);
`--log-file`; the ratatui screen with all seven requested content items; Kitty
and iTerm2 artwork with detection, sizing and lifecycle; the WebSocket
endpoint and its protocol crate; the standalone `openairplay1-dashboard` binary;
the tests above.

Out of scope: Sixel (few of the terminals in use need it, and it means color
quantization); mouse or keyboard interaction beyond quit; a log pane; any
artwork handling inside the library (it still ends at PCM + events);
mirroring the `SessionStarted` change into openairplay2; DACP transport
control. And for the dashboard seam specifically: **authentication or TLS on
the WebSocket** (loopback by default, and a reverse proxy is the answer for
anything else); a browser front end or any static-file serving; an HTTP
artwork URL; the dashboard controlling the receiver (it is read-only — no
volume, no skip); publishing either new crate to crates.io.

## Phases

1. **Library: progress and peer** — parse `progress:` in the
   `text/parameters` path, add `Event::Progress` (durations, not RTP
   timestamps), add `peer` to `SessionStarted` and mark that variant
   `#[non_exhaustive]`, bump to 0.2.0, update the receiver's existing match
   arms. Unit tests.
2. **The screen** — ratatui + crossterm, the centered layout with idle
   and playing states, all non-artwork content, `--log-file` and the logging
   redirect, terminal setup/restore including the panic hook, resize
   handling. `TestBackend` layout tests. *(Built as `--tui` on the receiver;
   phase 5 moves it.)*
3. **Artwork** — capability detection with the Kitty probe and env fallback,
   `--tui-images`, the two protocol encoders (JPEG decode for Kitty, direct
   passthrough for iTerm2), cell-size/aspect handling, image lifecycle
   (replace, clear, exit). Encoder and detection tests.
4. **Protocol crate and the receiver's WebSocket** — the
   `openairplay1-dashboard-protocol` crate (serde message types + snapshot),
   `--dashboard-listen ADDR` on the receiver, broadcast fan-out with a
   snapshot on connect, lag resync, ping/timeout. Round-trip and JSON-fixture
   tests, plus the real-socket integration tests above. The receiver still has
   `--tui` at the end of this phase; nothing is moved yet, so it stays
   reviewable on its own and bisects cleanly.
5. **The `openairplay1-dashboard` binary** — move `tui.rs` and `images.rs` into
   the new crate unchanged, add the WebSocket client with reconnect/backoff
   and the connection states, fold snapshots into `NowPlaying`, then **remove
   `--tui`/`--tui-images` from the receiver** along with its ratatui,
   crossterm and jpeg-decoder dependencies. README and CLAUDE.md updated for
   two binaries.

9. **Stop inventing the clock** — the display stops extrapolating once the
   last position report is stale, and `Flushed` freezes the position rather
   than clearing it. Dashboard only: no library change, no inference,
   `TestBackend` tests for the freeze and the resume. This is the phase that
   delivers the requested behaviour.
10. **A "paused" label, only if phase 9 isn't enough in use** — and only after
    the hardware capture above says what a paused sender does.
    `Event::Paused(bool)` inferred from the audio-stream gap, carried as
    `Message::Paused` plus a snapshot flag. Weigh the threshold heuristic
    against what the label actually adds before building it.

## Acceptance criteria

- The dashboard shows title/artist/album centered, plus receiver name, sender
  IP, format, volume, and elapsed/total, updating live across track changes;
  idle state before and after a session.
- Artwork renders as an image in Ghostty, updates on track change, disappears
  on the sender's `image/none` clear, and re-places correctly after a resize;
  a terminal without support shows the text-only layout with no stray escape
  bytes.
- The terminal is left clean on `q`, `Ctrl-C`, error exit, and panic.
- Without `--dashboard-listen` the receiver behaves exactly as today (logs to
  stderr, no listener, no terminal manipulation), and after phase 5 it has no
  TUI dependencies at all: `cargo tree -p openairplay1-receiver` mentions
  neither `ratatui` nor `crossterm`.
- A dashboard started **mid-track** shows the full screen immediately from the
  snapshot, including artwork; one started before the receiver connects when
  the receiver appears; and either side can be killed and restarted without
  the other needing a restart.
- Two dashboards on one receiver both stay current, and a dashboard that stops
  reading never stalls the receiver or the audio path.
- Library still ALSA-free and macOS-green; workspace clippy/fmt/rustdoc clean;
  no new library dependencies (the TUI ones live in the binary).
- Pausing the sender leaves the track and artwork on screen, freezes the clock
  where it stopped, and resumes cleanly — without the clock ever blinking out
  on the way into the pause, and without it advancing while nothing plays.
- Hardware validation with a real sender in Ghostty, per the plan above,
  including a pause/resume cycle and what the sender actually sends around it.
