# Plan: optional pincode protection for the receiver

- **Date:** 2026-08-04
- **Status:** proposed (needs Stefan's approval before implementation)
- **Scope:** this repository only. The pincode is a *protocol* property of
  the library (it is negotiated in the RTSP handshake, exactly like the
  `Apple-Challenge` today), so it lands in `openairplay1` and is surfaced by
  the receiver as a CLI flag (`--pincode`) and by embedders through the
  builder (`.pincode(...)`).

**Scope change this plan makes explicit:** `password protection` is currently
listed out of scope in [CLAUDE.md](../CLAUDE.md). This feature brings it in.
It remains out of scope for the *dashboard seam* — see Non-goals.

## Background

Today any client that can reach the receiver's RTSP port can stream to it,
and the only authentication on the wire is the `Apple-Challenge` /
`Apple-Response` exchange ([crypto.rs](../openairplay1/src/crypto.rs)), which
proves the *sender* is talking to a genuine AirPort — a device check, not an
access control. Anyone on the LAN can discover the receiver in the AirPlay
picker and start playing music through the speakers it drives. Stefan wants
the option to gate that behind a pincode.

The AirPlay 1 protocol has a password feature. The `_raop._tcp` TXT record
we advertise today pins it off — `pw=false`
([avahi.rs](../openairplay1/src/avahi.rs)); when a password is set the
receiver advertises `pw=1` **instead**, which tells Apple senders that the
receiver is protected and that they must authenticate (and, on older clients,
prompt for the password) before a stream will be accepted.

The crypto primitives the exchange needs already exist in the library: the
`rsa` + `sha1` dependencies used for OAEP-wrapping/unwrapping of the AES
session key, and `base64`. So this is mostly: thread the pincode through
config, flip the TXT record, gate the session at SETUP, and pin the exact
wire exchange a real sender uses.

## Goals

- A receiver configured with a pincode refuses to stream to a sender that
  has not authenticated, while behaving exactly as today for the discover /
  handshake / error flows.
- Without a pincode configured, **drop-in identical behavior**: same
  `pw=false` advertisement, same accept path, same event sequence.
- The pincode never appears in logs, in any RTSP response, or in the TXT
  record (the advertising boolean `pw` is not the secret).
- The pincode is settable by the standalone receiver via `--pincode` and by
  embedders via `Receiver::builder().pincode(...)`.
- The library stays ALSA-free and macOS-green; no new audio dependency.

## Non-goals

- **The dashboard WebSocket stays unauthenticated** (loopback by default,
  reverse proxy for anything else, per the TUI plan). Protecting it is a
  different problem with a different threat model and this plan does not
  touch it.
- No AirPlay 2 pairing, no per-device identity, no change to the existing
  AirPort-key `Apple-Challenge` device handshake (that stays, and stays
  outside the pincode gate).
- No DACP transport control, no `PAUSE` — unrelated.
- No pincode *entry* UI on the receiver side; the pincode is entered by the
  sender, out of band, as Apple intended.

## Design

### Config and the builder

`Config` gains the pincode, and the receiver advertises the password bit
from it:

```rust
pub struct Config {
    pub name: String,
    pub port: u16,
    pub mac: [u8; 6],
    /// `Some` → the receiver requires a pincode to stream; advertised as
    /// `pw=1`. `None` (default) → `pw=false`, today's behavior.
    pub pincode: Option<String>,
}
```

`ReceiverBuilder` gains `.pincode(impl Into<String>)`. The receiver passes
it into `Context`, the session gate reads it at SETUP.

`avahi::txt_records()` stays a free function (it is the TXT set both the
built-in publisher and host-owned mDNS use), but the `pw` record it emits
must now depend on the configured pincode. Today the free function has no
arguments; it becomes `txt_records(pincode: Option<&str>)` and
`Receiver::txt_records()` forwards `self.config.pincode`. The receiver's
host-owned-mDNS path (`advertise(false)`) keeps working because the host
folds `` `pw=1` `` / `pw=false` into whatever it advertises.

Computing the record:

```rust
fn pw_record(pincode: Option<&str>) -> String {
    match pincode {
        Some(_) => "pw=1".to_string(),
        None => "pw=false".to_string(),
    }
}
```

The pincode itself is **never** the advertisement.

### The gate

Authentication is checked at the point the listener's connection, having
announced, asks to stream — `SETUP` (in
[session.rs](../openairplay1/src/session.rs)), matching where the SDP/session
key is validated today. Until a connection authenticates it may do the
discovery warm-up (`OPTIONS`, `ANNOUNCE`, `GET_PARAMETER`, even metadata
`SET_PARAMETER`) exactly as now — none of that is a stream — but a `SETUP`
from an una authenticated connection is refused.

The wedge in `handle_setup`:

```rust
if let Some(pin) = &context_pincode {
    if !crypto::verify_pincode(pin, request) {
        warn!("SETUP refused: bad or missing pincode");
        return Response::new(401, "Unauthorized");
    }
}
```

The 401 mirrors the library's existing convention of refusing with a
non-2xx status (456 / 453 / 455 are already used) and is the natural "you
must authenticate" answer; the *exact* status code the client expects is
pinned in Phase 1 (see below) against a real sender.

### The wire exchange (working hypothesis — to be pinned in Phase 1)

This is the one genuinely uncertain piece, and per this repo's
evidence-first convention (the `progress:` plan reversed on a capture) it is
settled by measurement before implementation. The working hypothesis, from
the community RE of the AirPlay 1 protocol, is:

- A sender that discovers `pw=1` authenticates **inside the RTSP exchange it
  already makes**, delivering the password wrapped in the same RSA-OAEP
  primitive used for `rsaaeskey` — the receiver unwraps it with the AirPort
  private key already embedded, the exact `decrypt_aes_key` OAEP path, then
  compares the plaintext to the configured pincode.
- An unsuccessful or missing authentication is refused before `SETUP`
  succeeds.

The plan deliberately does **not** hard-code the container (header vs. body)
or the digest shape here; Phase 1 captures what a real sender actually emits
against a `pw=1` receiver and pins those exact bytes as a test vector before
any of it is implemented. If the capture contradicts the hypothesis (e.g.
the password is carried as plaintext base64, or as a challenge-response hash
of pincode+nonce rather than an OAEP wrap), Phase 1 records that and the
gate is built to the evidence.

### Comparison must be constant-time

The pincode is compared within an authenticated-ish exchange over the
network, so it must not leak a byte-by-byte timing signal that turns into a
remote oracle. Rust's `==` on `String`/`[u8]` short-circuits on the first
difference, so it is *not* safe here (the existing `apple_response` and
`decrypt_aes_key` don't compare secrets, which is why they are fine). Two
options:

1. Add the tiny `subtle` crate (`ConstantTimeEq`) — one dependency, the
   standard answer, no MSRV risk (`subtle` supports old Rust).
2. A hand-rolled constant-time compare over fixed-length byte strings.

`subtle` is preferred; a hand-rolled XOR-accumulate compare is short enough
that either is defensible, and the plan notes both but proposes `subtle`.

### No rate-limit redesign

A pincode can in principle be brute-forced over the network, but the AirPlay
flow naturally throttles it: each attempt is a new RTSP connection + full
handshake, and each SETUP attempt rejects after one shot. The library's
existing single-session gate already blocks concurrency. A per-IP auth-failure
counter is **not** in the first cut — it adds state and a lock to a path we
are still learning the shape of. It is noted under Follow-ups.

## Phases

Stacked PRs via `gh-stack`, per CLAUDE.md: this plan is the bottom PR of a
fresh stack; the phases follow stacked on top. Each leaves the tree green
(`cargo test`, `clippy -D warnings`, `fmt`) and the receiver verifiable.

### Phase 1 — pin the wire exchange (evidence + test vector)

Build a temporary probe: a `pw=1` receiver (just flip the TXT record on a
stock build) with `RUST_LOG=debug`, and capture what a real sender sends —
with a real iPhone/Mac and, if available, a capture from iTunes — driven by
the existing synthetic-sender helpers in `tests/`. Record in this plan's
Status block: which method/header/body carries the password, whether it is
OAEP-wrapped or a challenge-hash, what status the sender expects back on
success and on refusal, and whether a modern iOS sender actually offers a
pincode prompt on a plain RAOP receiver at all (see Risks). This phase
produces the **test vectors** Phase 2 implements against. It may add no
production code, or only enough to log the relevant bytes.

### Phase 2 — config plumbing

`Config.pincode`, `ReceiverBuilder::pincode`, `avahi::txt_records(pincode)`
with the `pw` record computed from it, `Receiver::txt_records()` forwarding,
and `--pincode` on the receiver CLI (usage string, parse, and a startup
`info!` line that confirms protection is on — **without printing the
pincode**). Update the receiver's `main.rs` builder wiring and the README /
CLAUDE.md "out of scope" language. Unit tests: `pw_record` flips, builder
round-trip, `--pincode` parse, `txt_records` includes `pw=1` with a pincode
and `pw=false` without. No behavior change yet — a configured pincode does
nothing until Phase 3, which is fine and keeps this phase reviewable.

### Phase 3 — the gate

Implement `crypto::verify_pincode(pin, request)` on the Phase-1 evidence,
wire it into `handle_setup` before the slot/sockets are acquired, and the
constant-time compare. Unit tests for the gate against the pinned vectors
(accept with the right pincode, refuse with a wrong one, refuse when absent,
malformed crypto material), plus a `handshake.rs`-style integration test: a
synthetic sender that authenticates completes `ANNOUNCE → SETUP → RECORD`;
one that doesn't is stuck before the stream. `SessionEnded` is *not* emitted
for a refused SETUP (nothing started); confirm the gate is checked before
`SessionStarted` and before the slot is acquired.

## Test strategy

- Unit: `pw_record` and `txt_records` (Phase 2); `verify_pincode` accept /
  reject / malformed against the Phase-1 vectors, and a constant-time property
  test asserting the compare does not early-return on a length-matching wrong
  password (Phase 3).
- Integration (`tests/handshake.rs`, `tests/robustness.rs` style): the
  pincode-protected server refuses an una authenticated SETUP with the pinned
  status and never emits `SessionStarted`; the authenticated sender streams
  end to end. These run through the existing `#[doc(hidden)]` server helpers
  on ephemeral ports, no ALSA, no Avahi.
- Regression: **no pincode configured** ⇒ the whole existing suite passes
  unchanged and the TXT is still `pw=false` (guards the drop-in claim).
- Hardware (acceptance): a real sender prompted for and accepts the pincode
  and streams; a second real client without it cannot; `RUST_LOG=debug` over
  the whole interaction contains no trace of the pincode.

## Acceptance criteria

- `cargo build --release && cargo test && cargo clippy --all-targets &&
  cargo fmt --check` green; library still ALSA-free and macOS-green
  (`cargo test -p openairplay1`), no audio-output dependency added.
- With no `--pincode`, behavior is identical to today — same TXT records,
  same events, same handshake, existing tests unmodified and green.
- With `--pincode`, a real Apple sender is prompted, streams once the pincode
  is entered, and cannot start a stream without it; the refusal is reflected
  in the RTSP status, and no `SessionStarted` is emitted for a refused
  session.
- The pincode appears nowhere in logs, responses, or the advertisement.
- `--pincode` is documented in the usage string and README; CLAUDE.md's
  "out of scope" line for password protection is replaced with a pointer to
  this feature and its confinement (library + receiver CLI only, not the
  dashboard socket).

## Risks / open questions

- **Does a modern stock sender even prompt?** This is the key validation
  risk. Old iTunes/AirPort definitely prompted and authenticated against
  `pw=1`; it is not yet confirmed that current iOS still offers a pincode
  entry for a plain AirPlay 1 RAOP receiver, or that it will present the
  receiver in the picker once `pw=1` is advertised. Phase 1 answers this
  *before* we build the gate; if iOS no longer prompts, the feature is
  scoped down to "protect against non-Apple and older clients" and that is
  recorded, not silently assumed.
- **Exact container and status.** The OAEP-wrap hypothesis and the `401` are
  starting points; Phase 1 pins them. Until the capture, no production code
  is written against either.
- **`subtle` dependency.** Small, standard, but a new Rust dependency — worth
  noting since the library's macOS portability criterion is about *audio*
  deps, and `subtle` is pure and portable (builds everywhere `rsa` does).
- **Plaintext pincode on the command line.** Visible in the process list.
  Acceptable for a speaker / personal receiver (a config-file or env-var
  source is an easy later extension and does not change the wire protocol);
  recorded here so it is a decision, not an accident.

## Follow-ups (not in this plan)

- Config-file / env-var pincode source.
- Per-IP auth-failure throttling if measurement shows brute-force is cheap.
- Protecting the dashboard socket (separate design, separate threat model).

## Phase 1 evidence (2026-08-05) — the `pw=1` probe against a real sender

Ran the Phase 2 build (`pincode-2-config-plumbing`, `--pincode 1234`) on
Stefan's LAN and connected a real sender. **Finding: a modern stock sender
ignores `pw=1` entirely.**

Capture: `User-Agent: AirPlay/950.7.1`, full handshake — `OPTIONS` ×3, an
`OPTIONS` with `Apple-Challenge`, `ANNOUNCE` (SDP with `rsaaeskey`/`aesiv`),
`SETUP`, `RECORD`, `SET_PARAMETER` (volume / `progress:` / DMAP metadata /
JPEG artwork), `FLUSH` with `RTP-Info`, then audio (1898 packets, played
normally). The handshake is byte-for-byte identical to an unprotected one:
**no credential appears anywhere** — no password header on any request, no
password in the SDP body, no challenge-secret exchange. The sender streamed
to the `pw=1` receiver as if it were open. (Assumes the phone read the
`pw=1` TXT the probe advertised; it connected straight to it.)

**Consequence: a pincode gate that refuses an unauthenticated SETUP breaks
modern Apple senders.** They never send a credential — there is no prompt
and nothing on the wire to authenticate with — so a rejecting gate would
lock them out with no recovery path. The approved Phase 3 (reject senders
that don't present the pincode) **cannot work as scoped**. This is exactly
the risk case the plan anticipated; it has now materialised on the primary
target platform.

Options, pending Stefan's decision:

1. **Drop the feature.** Modern senders already don't offer the legacy
   AirPlay 1 password, so `pw=1` is a no-op for them and there is nothing to
   gate. (Would cross-check with an *old* iTunes build, which is the one
   client the legacy flow historically targeted, before concluding.)
2. **Repurpose `--pincode` as a lockdown/deny-all**: refuse to stream to a
   sender that presents no credential. That blocks modern Apple senders
   too, so it is only useful against old iTunes / non-Apple clients that
   actually implement the `pw` exchange — close to "receiver off for modern
   devices".
3. **A different access control instead.** Every request in the capture
   carries `DACP-ID` and `Active-Remote` — an allowlist on the device id is
   a *device* allowlist, not a pincode, and would be a separate feature/
   plan (and doesn't map to the legacy AirPlay 1 password model).

No Phase 3 (SETUP gate) work proceeds until this is decided.

## Source verification (shairport-sync, 2026-08-05)

Cross-checked the classic AirPlay 1 password against `mikebrady/shairport-sync`
@ `master`. It supports a password, but the mechanism and expectation differ
from what this plan assumed, and the `pw` value is now known precisely:

- **The mechanism is HTTP Digest auth (RFC 2617), not a PIN-prompt flow.**
  In `rtsp.c`, `rtsp_classic_airplay_auth()`: when `config.password` is set,
  the server returns `401` with `WWW-Authenticate: Digest realm="raop",
  nonce="…"`; the client must retry with an `Authorization: Digest` header
  whose `response` is `MD5(hex(MD5(user:realm:pass)) : nonce :
  hex(MD5(method:uri)))`. The check gates method dispatch
  (`conn->authorized`). There is no "receiver shows a pincode for the user to
  type into the phone" step — that is AirPlay 2 HomeKit pairing, out of
  scope here. (it is skipped entirely for `ap_2` connections.)
- **The TXT value is `pw=true`, not `pw=1`.** `bonjour_strings.c` emits
  `pw=true` when `config.password != NULL`, `pw=false` otherwise. **Our Phase
  2 code advertises `pw=1` — that is wrong and should be corrected to
  `pw=true`, regardless of the direction decision.** This is a real bug in
  the current branch.
- **Working clients are non-Apple only.** `RELEASENOTES.md` credits only
  Android (AllConnect/Streambels) with password protection; iOS/iPadOS is
  never listed. So the server-side feature is real and implementable (MD5
  Digest), and would function for any client that speaks `Digest
  realm="raop"` — Android apps, old iTunes — but there is no evidence a
  modern Apple sender participates.

**Refined decision.** A real pincode implementation is possible: advertise
`pw=true`, and at SETUP gate on the Digest `Authorization` header using
`MD5(user:realm:pass)` with `realm="raop"` and a per-connection nonce. It
would protect against clients that *try the flow* (non-Apple, old iTunes),
which matches the original motivation (keep random LAN clients out). It will
not bind or prompt modern iOS, which appears not to do the classic flow at
all. To confirm modern iOS definitively: run a stock shairport-sync with
`--password` against the phone; if it answers the Digest 401 with an
`Authorization` header it supports it, otherwise it does not.
